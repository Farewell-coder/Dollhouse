## 一、核心规则（先看这个）

### 「人偶」vs「角色」—— 判定四问

按顺序问，**命中一条就停**：

| # | 这句话指的是…… | 结论 |
|---|---|---|
| **1** | App 里**那个实体**（包括它的图、它的库、它的记忆、它的动作） | **人偶** |
| **2** | **图/素材里被画出来的那个形象**（供切分、占比、轮廓识别用） | **角色** |
| **3** | 某个对象的 **name 值，会落库** | **不动**（名字是数据，不是术语） |
| **4** | **外部标品格式的专有名词**（角色卡、角色设定） | **保留** |

**为什么要这条分界线**：底栏 Tab 叫「人偶」、管理页标题叫「人偶」、设置入口叫「管理人偶」，
`AboutPage` 的自我介绍也用「人偶」—— 它是这个 App 的主词。
而「角色」在图稿语境（"这组图里认不出稳定的角色轮廓"）和外部格式语境（Tavern 角色卡）里是**准确的**，
一刀切成「人偶」反而错。

**四问的反面（看到这些别改）**：
- `角色卡` / `导出角色卡` / `提示词与角色卡` → 外部格式，改了就与外站对不上
- `角色设定` → 已定型的入口名/术语
- `永远不要跳出角色` → 扮演行为，与人偶实体无关
- `示例角色` → 是一只会出现在列表里的人偶的**名字**

### 三条纪律（踩过坑，写在这里）

1. **只改用户可见字符串**。不碰变量名、键名、日志、AI 提示词、注释。
   本项目有过「按 grep 结果批量修标点，结果改的全是 AI 提示词」的事故。
2. **Kotlin 块注释可嵌套**：注释里写 `/*` 会开启嵌套注释，把后面整段代码吞掉，编译报在文件末尾。
   改文案时一个字都别写进块注释里；要写说明用 `//`。
3. **改文案可能改出功能回归**：任何「默认文案」如果同时被代码当**判定值**用，必须一起改、且向后兼容。
   真实案例见 §三 的 T4。

### T4：`新的对话` → `新的会话`（7 处 + 1 处判定）

管理动作（重命名会话 / 清空全部会话 / 新建会话 / 历史会话 / 没有匹配的会话 共 29 条字面量，审计基线时 24 条）**已全用「会话」**，
只有「会话的默认标题」叫「新的对话」—— 列表项与操作名对不上。已改 7 处可见文案：
`ChatListData:127`、`ChatSessions:332/578/934/1081/1085`、`ConversationHistoryPage:53`。

> ⚠ **这条差点改出 bug，务必记住**：`ChatSessions.autoTitleIfNeeded()` 里有一句
> `if (!title.isEmpty() && "新的对话" != title) return` —— 它是"标题还是占位时，用首条消息自动命名"的判定。
> 只改文案不改它 → 新会话存的标题是「新的会话」、判定比对「新的对话」→ **永远不成立 → 自动命名彻底失效**，
> 而且用户只会觉得"自动命名功能没了"，没人会想到是文案改的。
> 处理方式：**比对目标跟着改，同时保留旧词**（`"新的会话" != title && "新的对话" != title`），
> 这样新会话正常、老用户已存的占位标题也还能被自动命名。

| **确认类按钮** | 三类，按"点击后发生什么"分：<br>·「**知道了**」= 一次性通知，点了只关窗（13 处调用点，另有 1 处是 `AppDialog.note()` 的 API 默认值）<br>·「**确定**」= 真有写操作/要拍板（`AppearancePage:578` 的颜色保存即此类）<br>·「**关闭**」= 用户正对着内容看、主动收起（调试状态、接口详情、预览页） | `好` 4 处已统一为「知道了」；`确定` 0 处改动（全是真写操作或 API 默认值）；`关闭` 8 处保留 |
| **取消** | 唯一否定按钮，无变体（`不了`/`算了`/`不用了` 全仓 0 条）。审计基线报 32 处，本文写作时实测 **52 处**（并行改动一直在加弹窗，词本身没分化） | ✓ 不必动 |

> **不要为了统一而统一**：确认按钮的统一只针对"点了只关窗"的那一类。
> 把真写操作的「确定」改成「知道了」，用户会以为只是关闭、结果数据被改了 —— 这是比不一致更严重的问题。
