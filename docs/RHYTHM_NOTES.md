# 留白韵律（RHYTHM）审计与调整

> 缘起：用户反馈「改了排布但不精致」。间距已经**落档**了（182→54，几乎全走 `DhDesign.Space`），
> 但「处处落档」不等于「有节奏」—— 一段很密、一段很疏，比全局 8dp 更有秩序感。
>
> 判断标准（任务书）：一个好的列表页，从上到下应该能看出**区块**，而不是一堆等距的行。
> 对照原则：`SPACING_MAP.md` 的 R7「组间距必须明显大于行间距」。
>
> **本轮的结论是：问题不在"没落档"，而在①少数漏网的硬编码值、②组间距与行间距拉不开差距。**

---

## 1. 三个页面的实际节奏

### 1.1 聊天列表 `ui/chat/ChatListScreen.kt`

从上到下的垂直间距序列（`PAD_H` = 16）：

| 位置 | 上间距 | 下间距 | 语义 |
|---|---|---|---|
| 顶栏 → 搜索框 | 顶栏自带 `bottom=4` | — | 标题与控件 |
| 搜索框 → 筛选条 | — | `md(12)` | **控件之间** |
| 筛选条 → 列表 | — | **`8.dp`（硬编码）** | 控件与内容之间 |
| 列表行内部 | `sm(8)` × 2 | — | 行内 |
| 行内标题 → 副行 | `3.dp`（硬编码） | — | 主次文字 |
| 行内副行 → 未读点 | `xs(4)` | — | 主次文字 |

**问题①：搜索框下方 12、筛选条下方 8。** 两者是同一层级的「控件 → 下一块」，
却给了两个不同的值，而且**更靠近内容的那一处反而更小**（8 < 12），
导致「筛选条和列表粘在一起、搜索框和筛选条之间反而松」—— 视觉上是反的。
这正是"落档了但不精致"的直接来源：两个值都在刻度上，但**用在了该统一的地方却没有统一**。

**问题②：列表行内部 3dp 是漏网的硬编码**（全仓 6/10 收敛时 3dp 不在扫描范围）。
它是「标题 → 时间/副行」的主次对，按 R10 应该是 `xs(4)`。差 1dp 肉眼几乎看不出，
但它是**唯一没走 token 的值**，属于「下一轮漂移的种子」。

### 1.2 聊天页 `ui/chat/ChatUi.kt`（**只读分析，未改** —— 见 §4）

| 位置 | 值 | 判断 |
|---|---|---|
| 空态 `EmptyHint` 顶部留白 | `80.dp` | 硬编码大值。空态居中是合理的，但 80 不在刻度上（应为 `xxl(32)` + 权重居中） |
| 摘要条 `top=10, bottom=4` | `10` / `4` | 上 10 非刻度（应 `md(12)`），下 4 已是 `xs` |
| 气泡内图片 → 文本 | `6.dp` | 主次内容对，应 `xs(4)` |
| 摘要「覆盖 N 条」 | `10.dp` | 块间距，应 `md(12)` |
| `LoadEarlierRow` 底 | `4.dp` | 已是 `xs` 等价，合格 |
| 消息块之间 | `2.dp` ×2 | 微对位，属 D1，**合理保留** |

**问题③：聊天页的「消息与消息之间」和「消息内部」几乎同值**（2dp vs 4~6dp）。
这违反 R7 的同一原则：**组间距（消息之间）必须明显大于行间距（消息内部）**。
结果就是任务书说的「连续多段一样疏」—— 一屏 10 条消息糊成一片，看不出哪是一条。

### 1.3 设置页 `ui/settings/ChatSettingsPage.kt`（**合格，未改**）

结构是 `DhKit.Card { Note → SwitchRow → Note }`，其中：

- 卡片之间：`DhGroup` 的 `bottom = cardGap(12)`
- 卡片内块之间：`Note` / 行自带的内边距

**这一页的节奏是对的**：卡片本身就是「区块」的强视觉分隔（圆角 + 描边 + 底色），
卡片间 12dp 加上边框的呼吸感，已经能让眼睛"换气"。**不需要为了节奏再加大** ——
再加大会让设置页变成"一屏只有两张卡"，反而失去信息密度。

> 结论：设置页是**对照组**。它证明「有区块容器时，组间距 12 就够」；
> 而聊天列表**没有**区块容器（纯行列表），所以它需要**用间距本身**造出区块边界 —— 这正是问题①②的根源。

## 2. 本轮实际改动（仅 2 处，都在 `ChatListScreen.kt`）

### 改动 1：筛选条下方 `8.dp` → `md(12)`（与搜索框下方统一）

```kotlin
// 改前
Row(Modifier.fillMaxWidth().padding(horizontal = PAD_H).padding(bottom = 8.dp), ...)
// 改后
Row(Modifier.fillMaxWidth().padding(horizontal = PAD_H).padding(bottom = DhDesign.Space.md.dp), ...)
```

**为什么**：搜索框下方已是 `md(12)`，筛选条下方却 8。两者是同一层级（控件 → 下一块），
统一到 12 后，**「顶栏 / 搜索 / 筛选 / 列表」四段之间的留白一致**，
筛选条不再紧贴第一条会话。这也是本次指令「拿不准时优先让留白充分」的直接应用。

### 改动 2：行内 `3.dp` → `xs(4)`（主次文字对）

**为什么**：这是全文件唯一没走 token 的垂直值。按 R10（主标题 → 次级说明）落 `xs`。
视觉差异 1dp 可忽略，但它消除了「下一个 3dp 从哪来」的漂移源头。

### 未改动（评估后认为不该动）

| 位置 | 值 | 理由 |
|---|---|---|
| 顶栏 → 搜索框 | 顶栏自带 `bottom=4` | 顶栏是**固定高度组件**，它的留白属于自身几何；调用点再补会双倍 |
| 列表行内部 `sm(8)` | `8` | 行内紧凑是对的（R3），行高已由 `DhRow`/`defaultMinSize(64)` 撑住 |
| 未读点与时间的 `xs(4)` | `4` | 主次对，正确 |
| 徽标 `padding(6,1)` | 6/1 | D4：与 999 圆角配套决定徽标尺寸（已在上一轮标注） |

## 3. 「区块感」的量化判据（供后续页面复用）

一个**有节奏**的页面，垂直间距应该呈现「阶跃」而不是「平铺」：

| 层级 | 期望值 | 判据 |
|---|---|---|
| 页面级区块之间 | `xl(24)` ~ `xxl(32)` | 相邻两个"大块"（顶栏区 / 搜索区 / 列表区） |
| 卡片之间 | `cardGap(12)` | 已有 `DhGroup` 统一，不必逐页改 |
| 卡片内块之间 | `md(12)` | R4 |
| 行内元素 | `sm(8)` | R3 |
| 主次文字 | `xs(4)` | R10 |

**反例特征（本轮发现的两类）**：
1. **同一层级用了两个不同的值**（搜索框 12 vs 筛选条 8）→ 视觉上"该紧的不紧、该松的不松"
2. **组间距 ≈ 行间距**（聊天页消息间 2 vs 消息内 4~6）→ 内容糊成一片，没有区块

## 4. 为什么没有改 `ChatUi.kt` 和 `ChatSettingsPage.kt`

- **`ChatUi.kt`**：本轮任务书的排除清单明确列了它（chat-contract 在改圆角）。
  上面 §1.2 的三条问题**已定位到具体行**（375 / 552 / 556 / 714 / 904 / 964），
  但改它是**跨任务写入冲突**，留给 chat-contract 或下一轮单独做。
- **`ChatSettingsPage.kt`**：分析后判定节奏**已经合格**（有卡片容器做区块），
  按「拿不准时不动」的原则不改 —— 为了"统一"而给合格的页面再加间距，是过度设计。
