## ⚠️ §0 先读：验证工具本身有个坑，会让你做出错误结论

**`uiautomator dump` 给的不是布局边界，是无障碍边界。**
Compose 会把**小于 48dp** 的语义节点，以元素中心为基准**对称外扩到 48dp**。

```
布局值 = dump值 ∓ (48dp − 元素实际尺寸) / 2        // 左/上减，右/下加
```

- 真实代价：36dp 头像 dump 报 `x=30`，我据此判「顶栏左移 6dp」，白查一轮（见 §6 第 1 条）。
- **要判"布局有没有偏"，就量同一行里一个 ≥48dp 的元素**（卡片边缘、搜索框、输入框）。
- 量小图标 / 小药丸的位置 → **一定是假偏移**。

## §1 本轮修了哪些功能缺陷（**先验这一节**）

> 这 6 条是用户能直接感知的"东西坏了"，比任何视觉细节都靠前。
> 都不是新功能，是**原本承诺了但实际不生效**的东西。

- [ ] **FD-01 遮罩滑条 8% 以上完全失效**（拖了没反应）
  - 旧逻辑：`cap = (100 - imgAlpha) * 255 / 100`；图 92% 时 `cap` 只剩 7.8%，而 `worst` 恒接近满值
    → **k ≥ 8% 就撞天花板，从 8% 拖到 100% 渲染一模一样**。
  - 已修：删掉 `scrimCap`，改纯线性 `alpha = k * 255 / 100`。
  - **验法**：遮罩拖到 30% / 60% / 100%，三档必须**肉眼明显不同**。（对应 §3 背景-02）
- [ ] **FD-02 「弹窗透明度」对 Compose 弹窗不生效**
  - 旧逻辑：`DhForm.Alert` 直接用了 `c.sheet`、**没过 `dialogTint`** → 滑条只对 View 弹窗有效。
  - 已修：新增顶层 `dialogSheet()`，`Alert` / `show` / `AppDialog` 三处共用一份颜色真源。
  - **验法**：弹窗透明度调到 60% → **新开**一个弹窗，它必须跟着变透。（对应 §3 弹窗-01）
- [ ] **FD-03 说说页把「默认配置」当"没有真实人偶"**（P0 级死路）
  - 场景：队里只有一只标题叫「默认配置」的人偶时，旧判据判成"没人偶"，直接进死路。
  - **验法**：只留一只「默认配置」→ 进说说页 → 必须正常出内容/正确空态。
- [ ] **FD-04 「聊完一轮就记下来」是错的**（用户对"自动记忆"的理解与实现不符）
  - 实际行为：取**最后 6 条**消息（`ChatHistoryStore` 里 `h.length() - 6`）+ 受 `MemExtractGate` 的**间隔门槛**约束
    （设置页 5/10/20/30/60/120 分钟）；从来没抽过 → 立即抽一次；时钟回拨 → 重新起算不永久停摆。
  - **验法**：把「保存间隔」设为 60 分钟，连聊三轮 → **只应产生一次**记忆抽取；
    改成"从未抽过"的新装状态 → 第一条回复后应立刻抽一次。
  - 这条也是**文案口径**问题：如果界面上还写着"聊完一轮就记下来"，那是在说谎。
- [ ] **FD-05 `TAIL` 与 `PAGE` 不一致，让「加载更多」永不触发**
  - 旧：每人偶只取尾部 12 条，但分页步长 30 → 第一页就吃完了，永远没有下一页可加载。
  - 已修：`TAIL_PER_DOLL = 30`、`PAGE = 30`（现已一致，见 `SocialPage.kt:140/146`）。
  - **验法**：记忆条数 > 30 时，滚到底必须出现「加载更多」且点了真能加载。
- [ ] **FD-06 `hasKey` 不能单独判断「能不能记事」**（第二个死路）
  - 有 Key 但**关了自动保存** ≠ 没有 Key；旧判据把两者混成一个"不能记事"，用户永远等不到内容。
  - 已修：说说页空态按**真实状态**分 4 级（没人偶 / 没 Key / 关了自动保存 / 条件齐了还没内容）。
  - **验法**：关掉「自动保存记忆」→ 进说说页，文案必须说"你关了自动保存"，而不是"没有 Key"。

## §2 P0 必须验（会崩或功能不可用）

- [ ] **P0-01 `[提交]` 聊天背景裁剪页：一进页面不崩** ← 本轮最重要的 1 条
  - 背景：`buildUi()` 换成 `ComposeHost.createView(this)` 时**漏了 `ComposeHost.installForActivity(this)`**。
    本页继承 `android.app.Activity`（不是 `ComponentActivity`），decorView 上没有 `ViewTreeLifecycleOwner`
    → ComposeView 一 attach 就抛 `ViewTreeLifecycleOwner not found from DecorView` —— **必然崩**。
  - 已修（`134fc93`），但**修复本身要靠真机确认**。
  - ⚠️ 若崩，报错关键字：`ViewTreeLifecycleOwner not found from DecorView`。
- [ ] **P0-02 `[提交]` 裁剪页完整链路**：进页 → 换图 → 单指拖动 → 双指缩放 → 保存 → **回聊天页背景立刻变**
  - 保存链路三段都不能少：`GlobalBackground.release()` → `refreshAll()` → `ThemeRefresh.bumpAll()`
    （第三段是让 Compose 侧"要不要带可读带"重新求值；少它 = 图换了但带子没出现）。
- [ ] **P0-03 `[提交]` 封面裁剪页**（`CoverCropActivity`）：进得去 → 两步状态机 → 保存不崩
  - 若看到"文案与几何的步骤对不上"，说明有人把 `step` 改成 Compose 状态了（它必须保持普通 `Int`，
    保存时会临时改成 0/1/2 借它算选区再还原）。
- [ ] **P0-04 `[提交]` 说说页 FD-03 / FD-06 两条死路都不再出现**
- [ ] **P0-05 `[提交]` 桌宠输入条 Compose 化**：能打字、能发送、不吞字、光标正常（详见 §3 桌宠-13）
- [ ] **P0-06 `[提交]` `AppDialog` 三种形态**（`note` / `confirm` / `custom`）都能弹、都能关、回调都对
  - 收拢后 `UiKit.showDialog` 真实调用已归零 → **全 App 弹窗都走这一个组件**，它坏了是全站性的。

## §8 已知但不修（附理由，防止下一轮重复讨论）

- [ ] **静默时段的 12/24 小时制不跟随系统**
  - **理由**：这不是"显示格式"问题，是**数据迁移** —— 存储、输入、显示三处耦合在一起
    （存的是字符串还是时间戳、用户手输的合法性校验、旧数据怎么迁）。改显示层会让旧数据含义漂移。
  - 结论：**本轮只修了 2 处纯显示**，静默时段维持现状，需要单独一轮带数据迁移方案。
- [ ] **`GlobalBackground` 的 24×24 采样清理**
  - **理由**：本机**没有可用的编译器 / aapt2**（`aapt2` 二进制起不来），改这块无法本地验证。
    采样清理属于"算法正确性"问题，验证不了就不动 —— **留着比删错强**。
- [ ] **`CoverCrop` 的 inset 被 96/170 上限吃掉**
  - **理由**：当前栏高（62 / 124）低于下限，**被 `max` 吃掉 → 栏高对构图零影响**，行为是对的。
    真正的风险是未来有人"顺手调小"这两个下限，届时栏高会突然影响构图。
  - 结论：**保持现状**，把这条写进注释/清单即可（见 §6 最后一条）。
