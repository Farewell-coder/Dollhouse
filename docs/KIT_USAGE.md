# Dollhouse · 组件库使用量与绕过审计

> 本文对应 `tools/kit_usage_audit.py`，**可随时复跑**：
> ```
> cd <repo>
> python3 tools/kit_usage_audit.py                  # 完整表格 + 清单
> python3 tools/kit_usage_audit.py --quiet          # 只给结论（CI 用）
> python3 tools/kit_usage_audit.py --update-baseline # 确认接受新基线后更新
> ```
> 退出码：`0` = 无回退；`1` = 调用数下降或转发链断裂；`2` = 数据源缺失。

## 一、为什么需要这个审计

本项目最大的一次返工是：`ui/kit` 组件库建好了，但 **8 个组件的库外调用全是 0** ——
规范立在那儿，页面一个都没用。后来靠 `DhKit` 的「转发」机制接上 260 处调用：
页面写 `DhKit.ValueRow`，它的内部调 `ui/kit.DhRow`，样式只有一份。

这个机制有一个致命弱点：**转发是"软"的**。
如果有人嫌麻烦，把 `DhKit.ValueRow` 里的 `kit.DhRow(...)` 换回自己画的 Row，
代码照样编译、界面看着差不多、测试全绿 —— 但规范已经悄悄失效了。

现有门禁都发现不了这件事：
- `ui_audit.sh` 的 B 组只检查**定义是否存在**（`grep -q 'fun DhButton('`），
  不查"有没有人调"、更不查"转发还在不在"。
- `input_audit.py` / `state_audit.py` 查的是各自领域的实现细节。

本脚本补的正是这个缺口，并把**当前数字钉成基线**：调用数下降即报错。

#### 订正记录（本文件早前版本的错误）

本文件 2026-11-07 早前版本曾写「`SwitchRow` / `PermRow` 从未转发」，
并称任务简报里「每个转发 2 次」的说法不成立。**这两条现在都已过时，原因不同**：

1. **早前版本的正确部分**：当时（约 15:30）实测这两个函数内部确实**没有任何** kit 调用。
   文件里另有 4 处 `kit.Dh` 字样是**注释里的路径提及**（如 `` `ui/kit.DhGroup` 是规范源 ``），
   把注释当调用就会得出「每个 2 次」。
2. **现在已不同**：`SwitchRow`（DhKit.kt:843）与 `PermRow`（DhKit.kt:896）
   **已被真正转发**到 `kit.DhRow`，转发链 5/5 完整。

**教训**：这类"进度类"描述会随他人并行改动迅速失效。
本文件里凡是「X 未转发 / 正在处理」这类状态，**一律以脚本输出为准**：

```bash
python3 tools/kit_usage_audit.py | sed -n '/K2 转发链/,/K3/p'
```

脚本的 `K2b` 段会在函数「已开始转发」时提示「可从事先登记表中移除本项」——
这正是本次状态变化的信号。

## 四、按钮体系：唯一未收口的大块

`DhButton` 是 **0 调用**，但全仓有 **54 处**药丸按钮，全部来自四个工厂：

| 工厂 | 形态 | 调用点 |
|---|---|---:|
| `DhForm.PrimaryChip` | 999 药丸 / accent 实心 / pad 16×9 | 18 |
| `DhForm.OutlineChip` | 999 药丸 / card 底 + line 描边 | 15 |
| `DhKit.OutlineChip` | 999 药丸 / cardUp 底 + line 描边 | 17 |
| `DhForm.SubmitButton` | 999 药丸 / 内边距撑高（**无固定高**） | 2 |
| `DhForm.Chip` | 999 药丸 / 小号 | 2 |
| **合计** | | **54** |

（全仓 `RoundedCornerShape(999)` 共 52 处 —— 与 54 不矛盾：这个数只统计
`RoundedCornerShape(999)` 字面量，而 `DhForm.Chip` 少数几处共用同一个 shape 变量。）

**与设计稿的差距**：设计稿写的是「Buttons — **one height, 44dp**」，
即按钮统一 44dp 高 + 12 圆角。`kit.DhButton` 正是这么实现的，却没有页面在用；
实际的 54 处按钮全是 999 药丸 + 内边距撑高，`SubmitButton` 连固定高度都没有。

**结论**：行 / 卡片 / 输入框都已转发到 kit，**只有按钮体系没统一**。
统一它们是独立工程（改 54 处、影响所有页面的点击区与视觉），本轮**只量化，不做统一**。

## 五、绕过检测

### 5.1 自建按钮候选（16 处，**只作线索，不计失败**）

判据：同一条 Modifier 链里同时出现 `pressable`/`clickable` + `background` + `clip(圆角)`。

**为什么不计失败**：这个形态无法可靠区分"按钮"和"可点的非按钮"。实测抽查：
- `DhForm.kt` 的 `DialogButton` —— **真按钮**；
- `DollGroupPage.kt` 的可点条目 —— **真按钮**；
- `ChatListScreen.kt` 的头像按钮 —— 是头像，不是按钮；
- `ChatUi.kt` 的提示条 —— 是可点提示条，不是按钮。

把无法区分的形态设为硬失败，门禁会长期报红 —— **那等于没有门禁**
（这是本项目已经吃过两次的教训）。因此本项只输出清单，供后续人工收编。

### 5.2 裸 `Switch(`（1 处，仅作线索）

`ui/theme/UiKit.kt` 里 1 处。多数裸开关有合理场景（卡片右上角等），故只统计。

### 5.3 输入框 / 空态（**引用既有脚本，不重复实现**）

| 检测项 | 做法 | 当前结果 |
|---|---|---|
| 输入框绕过入口 | 引用 `tools/input_audit.py` 的 I6 | PASS 22 / FAIL 0 |
| 空态骨架 | 引用 `tools/state_audit.py` 的 S3/S4 | 已规范 6 / 自建 0 / 纯空白 0 |

**为什么用 `subprocess` 而不是 `import`**：
这两个脚本是「模块级就执行」的写法（顶层求值 `sys.argv` + 全局 `results`），
直接 import 会污染本进程的 argv 与全局状态，且它们的 `main()` 会立刻跑一遍。
`subprocess` 还有额外好处：顺带验证"那两个脚本自己是否健康"。
代价是每次多起两个解释器（毫秒级），值得。

## 六、防回退：退出码与基线

脚本把当前数字写入 `tools/kit_usage_baseline.json`，
之后每次运行都与基线比对：

- **调用数下降** → 判失败（`exit 1`）。有人删掉一处 `DhRow(...)` 调用、或把转发改回自绘，
  数字会掉，立刻暴露。
- **转发链断裂** → 判失败（`exit 1`）。这是最关键的一项。
- **调用数上升** → 只报告（`↑+N`），不失败。
- **有意减少**（如收编后删掉重复实现）→ 用 `--update-baseline` 接受新基线。

## 七、自测证据（反向验证）

前几轮已经出现过多次"检查脚本自己假绿"，所以本轮对**注入 → 报错 → 恢复 → 通过**
两个方向都做了验证。所有注入均已逐字节还原（`git diff` 为空）。

| # | 注入的缺陷 | 期望 | 实测 |
|---|---|---|---|
| 1 | 注释掉 `ActionRow` 内的 `kit.DhRow(` | 报「转发链断裂」 | `发现 2 类问题：kit 调用数回退 1 项 + 转发链断裂：ActionRow`，**exit 1** ✓ |
| 2 | 恢复 | 回到基线、exit 0 | 通过，**exit 0** ✓ |
| 3 | 注释掉一处 `DhDivider(`（仅回退、不断链） | 报「调用数回退」 | `发现 1 类问题：kit 调用数回退 1 项`，**exit 1** ✓ |
| 4 | 恢复 | 回到基线 | 通过，**exit 0** ✓ |

第 1 项同时触发了两条判据（转发链断裂 + DhRow 计数下降），这是符合预期的：
转发点本身就是一处 `DhRow` 调用，断链必然伴随计数下降。

### 7.1 本轮修掉的三个自身缺陷

写脚本时踩到并修掉的（都是"判据与代码脱节"类）：

| 缺陷 | 表现 | 修法 |
|---|---|---|
| 转发链用 `kit.DhXxx` 匹配 | 源码里实际是 `com.dollhouse.app.ui.kit.DhRow(`（中间有点），按简报写法会**漏判全部转发** | 正则同时接受全限定与短名 |
| `str(p).parent` | `Path` 对象被 `str()` 后取 `.parent` → `AttributeError`，脚本直接崩 | 改用 `p.parent` |
| 自建按钮用 600 字符窗口取样 | 窗口跨函数，把 `fun Chip(` 定义行、底栏胶囊容器都算成"自建按钮"（17 处里大半是误报） | 按括号深度精确取 Modifier 链 |

另外修了一处**性能**问题：原实现每轮扫描都重新读 275 个文件（约 3.3M 字符），
总耗时超过 60 秒。加入内容缓存 + 合并正则后降到约 15 秒。
**门禁脚本一旦慢到几十秒，就会有人开始跳过它 —— 那等于没有门禁。**

## 八、后续收编建议（按优先级）

1. **按钮体系（最大缺口）**：54 处药丸按钮 → 统一到 `DhButton`（44dp / 12 圆角）。
   建议分批：先 `SubmitButton`（2 处，最不符合规范，且是"提交"这一唯一主动作），
   再 `PrimaryChip`（18 处），最后 `OutlineChip`（32 处）。
   **这一步会改变所有页面的视觉，需与设计稿确认"药丸 vs 圆角矩形"的取舍。**
2. ~~**`SwitchRow` / `PermRow` 转发**~~ —— **已完成**（DhKit.kt:843 / :896 已调 `kit.DhRow`）。
3. `DhIconButton`（0 调用）：确认是否真需要 —— 页面在用的图标按钮都走 `DhKit.IconButton`，
   若两者语义重复，应合并而不是并存。

## 九、边界

1. 本脚本**不做**静态类型分析，只做源码级文本判定；不能证明代码可编译。
2. 「经转发到达」的口径依赖 `tools/kit_usage_audit.py` 里的 `FORWARD_CHAIN` 表。
   该表现已同步为 5 条（`KNOWN_NOT_FORWARDED` 已清空），
   因此 `SwitchRow`(34) 与 `PermRow`(4) 已计入 → 经转发合计 **221**（DhRow 169 + DhGroup 52）。
   **若今后再给某函数加上转发，务必同步这张表**，否则统计会静默少算。
   脚本在 K2b 里会提示「已开始转发」，作为更新表的提醒。
3. 「自建按钮」的 16 处是**线索**不是定论，需人工判断。
4. 本脚本不检查设计令牌是否被绕过（那是 `design_parity.py` 的职责）。
